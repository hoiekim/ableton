# Session Player design

The Session Player is an AI band member for Ableton Live. It listens to what
the other tracks play, decides bar by bar what its own part (drums, bass, keys
or guitar) should play, and writes each decision as a MIDI clip that Live
starts on the next bar.

Goals, in order: low latency, accurate decisions, programmability, good UX.
Reuse existing tools and Live's own features rather than building from
scratch.

## What shaped it

| Finding | Consequence |
|---|---|
| Live 11.3 bundles Max 8.5.8 with Node for Max on Node 16.6, too old for modern packages. | Devices stay thin (no Node for Max); all logic runs in the Bun server, which already talks to Live through the LiveAPI.amxd bridge. |
| TypeSafe's Jev is a decision model: given a state and typed questions it picks one of up to 255 named options (`choice`), scores (`score`) or says yes/no (`noul`). It can't write notes. Measured: 60–190 ms per call. | Each instrument has a library of named, described patterns. Jev picks one; code renders it on the right chords. |
| Hosted or local LLMs take roughly 2–8 s for a bar's worth of notes; a bar at 120 BPM is 2 s. | No LLM sits in the per-bar path. |
| In Live 11, MIDI routed from another track arrives after that track's MIDI effects. | A small "Session Input" device placed first on a source track is the pre-effects tap. |
| A clip with 1-bar launch quantization starts exactly on the bar. | Decisions are written as clips and fired early; Live does the timing. A late decision just lets the current clip loop. |
| Max ships `fzero~` for monophonic pitch; polyphonic transcription (basic-pitch) works in 2-second windows. | Audio input is one note at a time for now. |
| The official TypeSafe SDK reads response bodies in a way Bun rejects ("Body already used"). | The server calls Jev's REST endpoint (`POST /v1/systemone`) with `fetch`. |

## Architecture

```
Source track:  [Session Input] -> its effects -> instrument       (MIDI, or Session Input Audio on audio tracks)
                      | OSC over UDP 9101: notes (or pitch readings) stamped with Live's song position
                      v
Bun server:  listen -> cut into bars -> analyze (chords, key, loop, rhythm, energy) -> describe as text
             -> decide (local rules or Jev: pattern, energy, fill) -> render on the upcoming chords
             -> write a clip into the player track's slot ring and fire it, through the LiveAPI.amxd bridge
Player track:  [Session Player] (settings as Live parameters) -> instrument; Live starts the clip on the bar
Web page:      Session panel with each decision, its timing and the text the model saw
```

### Devices

Generated by [scripts/build-devices.ts](../scripts/build-devices.ts) into
[devices/](../devices) as unfrozen `.amxd` files (`ampf` + `meta` + `ptch`
chunks holding the patcher JSON). The build checks every patch cord against
the boxes' inlets and outlets. The server recognizes the devices by parameter
name, so renaming a device in Live is fine; each parameter's short name equals
its long name, so either one matches.

| Device | Type | Parameters | Sends |
|---|---|---|---|
| Session Player | MIDI effect, before the player's instrument | `SP Instrument` (Drums/Bass/Keys/Guitar/Auto; Auto is last so older devices keep their setting), `SP Active`, `SP Lookahead` (1–4 bars), `SP Length` (1/2/4-bar clips), `SP Join` (bars to listen first), `SP Energy` (Auto or 1–10) | nothing; the server reads and observes the parameters through the Live API |
| Session Input | MIDI effect, first on a source MIDI track | `SPI Role` (Auto/Bass/Chords/Melody/Drums), `SPI On` | every note-on/off |
| Session Input Audio | audio effect, first on a source audio track | `SPI Role`, `SPI On`, `SPI Threshold` (dB) | `fzero~` readings every 10 ms, and onsets |

### OSC messages (UDP 127.0.0.1:9101)

Ticks are Live's song position from Max's `transport` object, at 480 per
quarter note. `deviceId` is the device's Live API id, which the server maps to
its track.

| Address | Arguments | From |
|---|---|---|
| `/sp/note` | deviceId, pitch, velocity (0 = off), ticks | Session Input |
| `/sp/pitch` | deviceId, hz, amplitude, ticks | Session Input Audio |
| `/sp/onset` | deviceId, ticks | Session Input Audio |
| `/sp/hello` | deviceId, `midi` or `audio` | both, every 2 s |

### Server modules ([src/server/session](../src/server/session))

| File | Role |
|---|---|
| `engine.ts` | Owns everything: finds Session devices in the set, receives OSC, counts bars while Live plays, drives one Player per Session Player device, publishes state to the web page. |
| `listen.ts` | Decodes OSC (`osc-min`) and cuts note events into bars; notes still sounding carry into the next bar as held notes. |
| `audio.ts` | Turns pitch readings into notes: a pitch must hold for 2 readings to start, 3 to change; a level threshold with 4 dB hysteresis ends notes; onsets re-attack. |
| `analyze.ts` | Per bar: each part's role, onsets on a 16-step grid (rounded to the nearest step), register, polyphony, velocity; the chord (Tonal's `Chord.detect` on a duration-weighted pitch-class profile, preferring the bass note as root); the key (Krumhansl–Schmuckler over recent bars); energy; and the chord of upcoming bars. |
| `state.ts` | The text the decision model reads. Every number is worked out in code; the model only reads. |
| `patterns/` | The pattern library and its renderers. |
| `providers/` | `local.ts` (rules) and `jev.ts`, behind one `DecisionProvider` interface. |
| `player.ts` | The scheduler: when to decide, writing and firing clips, misses, latency learning. |
| `config.ts` | Defaults, merged with [session.config.ts](../session.config.ts) and environment variables. |
| [live.ts](../src/server/live.ts) | Bridge additions: Session device parameters, and clip operations (`clipSlots`, `writeClip`, `fireClip`, `stopTrack`). |

## Instrument detection

The player reads the first instrument after its device on the track, so the
decision model knows what it is playing.

- **When it's read:**
  - When the devices after the Session Player change, after they settle for 0.4 s.
  - Every time playback starts, which catches a sample dropped onto a pad or a swapped preset.
- **What's read** (`readInstrument` in [live.ts](../src/server/live.ts)). Each
  property is asked only of the devices that have it, because Live logs an
  error otherwise.
  - **Top-level Drum Rack:** its 128 pads (note and name). A pad counts as loaded
    when it's named after one of the rack's chains.
  - **Drum Rack inside an Instrument Rack:** its chain names only. Live 11 reports
    no pads for a nested rack, and has no way to say which note plays a chain.
  - **Instrument Rack:** its chains (up to 8), and the instruments in them (up to
    3 racks deep).
  - **Simpler:** its sample's file name.
  - **Operator, Analog, Wavetable, Drift, Simpler and Sampler:** their amp-envelope
    parameters (`Ae`, `AEG1`, `Amp`, `Env 1`, `Ve` …). Names are read first, then
    values for at most four parameters, because a synth can have hundreds of
    parameters, all read on Live's main thread.
- **What's made of it** ([instrument.ts](../src/server/session/instrument.ts)):
  - **Drum sounds.** Each pad gets a role (kick, snare, clap, rim, closed or open
    hat, ride, crash, tom, shaker, conga, percussion, effect) from its name, else
    from its General MIDI note. The patterns then play the kit's own notes. A sound
    the kit lacks uses a stand-in, such as clap on the snare or ride on the closed
    hat. With a nested rack, the sounds are named but their notes are assumed from
    the standard layout, and the text says so.
  - **Melodic sounds.** Tags come from preset, rack, chain and sample names: bass,
    pad, pluck, piano, electric piano, organ, bell, mallet, lead, strings, brass,
    guitar. Then the envelope adds: slow attack, long release, dies away quickly.
    Its units are guessed (milliseconds for large ranges, otherwise a position in
    the range), so names always win.
  - **Auto role.** A Drum Rack or Impulse plays drums, a bass sound bass, a guitar
    sound guitar, and anything else keys.
- **How it reaches the decision model:**
  - The state text ends with "Your instrument: …", e.g. `Drum Rack "808 Core Kit": kick "Kick 808" C1, snare …`. Notes are named the way Live labels them.
  - **Drum options:** patterns that need sounds the kit doesn't have are dropped,
    and the percussion and tom grooves are offered only with those sounds. Each
    option names the pads it plays, e.g. "Plays: kick "Kick 808" C1, clap on
    "Snare Tight" D1, …".
  - **Melodic options:** each pattern is tagged sustained, rhythmic or busy, and
    its description says how well that suits the sound. For example, "Poor fit:
    fast notes blur on this slow-attack sound". The local rules weigh the same fit.
- **Plugins and Max instruments:** only their names are used.

## Per-bar pipeline

1. **Listen.** Notes arrive stamped with Live's song position, so their
   timing doesn't depend on network delay. When a bar ends, its notes are cut
   out per input. Notes that arrive a moment before the server notices Play
   are kept.
2. **Analyze.** The bar in progress counts too: decisions come late in the
   bar, when most of it has been heard. The next bar's chord comes from the
   repeating chord loop when there is one. The loop is judged by the unbroken
   run of recent bars that repeat, so one misheard bar doesn't hide it and a
   change of progression ends it at once. Otherwise the latest chord is
   assumed to continue.
3. **Describe.** For example:
   ```
   The next bar is bar 17 of the jam. Tempo 120 BPM, 4/4 time. Key: C major.
   Chords in the last 4 bars: G, Am7, Fmaj7, C. They repeat every 4 bars (sure).
   Chord for the next bar: Am7 (predicted from the repeating chords).
   Band energy: 6 of 10, steady.
   Bass (Bass): moderate, eighth notes, 8 new notes, low register, loud.
   Chords (Keys): sustained chords, 3 new notes, middle register, medium.
   You play guitar. Your last bar: strum-quarters at energy 6. Bars since your last fill: 3. The next bar starts a new 4-bar phrase.
   ```
4. **Decide.** One Jev call per decision with three questions:
   - `pattern` (`choice`): the instrument's pattern ids with their descriptions, plus `hold` (keep the last part).
   - `energy` (`score`): ten described levels. Skipped when the device fixes energy.
   - `fill` (`noul`): fills belong in the last bar of a phrase.

   Local rules decide instead when Jev is unsure (confidence below 0.25), errors, names an unknown pattern, or would answer too late. The local rules:
   - Match energy to the band.
   - Fill the space the band leaves.
   - Mostly stay on the current pattern, changing at phrase starts.
   - Fill at phrase ends.
5. **Render.** The chosen pattern is played on the predicted chord of each bar
   of the clip, with tones placed by voice leading. Energy scales velocity and
   density. A fill replaces the clip's last beat, and the player allows one only
   in the last bar of a phrase. Drums open with a crash after a fill. Rendering
   is seeded per bar, so it's reproducible.
6. **Write and fire.**
   - **Where:** clips go into the player track's last 4 slots in turn, never the slot that is playing.
   - **Name:** each clip is named after its decision, e.g. `SP 17 strum-quarters Am7 e6`.
   - **Launch:** clips are created with 1-bar launch quantization and looping on.
   - **Kept clips:** when a new decision would sound the same as the looping clip, nothing is written. This saves undo steps.
   - **Never fired:** a clip is never fired while Live is stopped, which would start the transport. It's also never fired within 25 ms of its bar, which would risk starting a bar late.

## Timing model

- **As late as possible.** Each bar is decided as late as the expected times
  allow, for the most context. The lead time is the slowest of the last 20
  decision times, plus the usual clip-write time, the fire margin (150 ms) and
  one engine tick. The slowest, not a percentile, because network answers have
  long tails and a late answer is wasted.
- **Lookahead.** This caps how early a decision may start, and how many run at
  once. A model slower than a bar still keeps up when Lookahead is raised.
  Clips are still committed in order: one waits for its bar at a time, since
  firing another would replace it.
- **The playhead.** It's extrapolated between Live's position reports from
  wall-clock time and tempo.
- **Missed bars.** If a decision misses its bar, the current clip keeps
  looping. If a decision arrives after its bar has started, its choice is
  reused for the next bar.
- **Learning latency.** A slow model's request is never abandoned at the
  deadline. Local rules answer in its place, but the real duration is
  recorded, so the next decision starts early enough. With a 1.5 s model at
  120 BPM, Jev decided every bar from the third bar on.

## Style direction

The web panel has a Style box for free text that applies to every player, such
as "funky 70s soul, laid back". It's sent over the socket, kept in memory by the
engine, and used from the next decision on:

- **Jev:** it reads the text as the first line of the state, and every question
  begins "The musician wants: …". Follow it.
- **Local rules** ([style.ts](../src/server/session/style.ts)): genre words favour
  that genre's patterns strongly enough to beat sticking with the current one,
  and mood words move energy by ±2.

## Programmability

- **Settings:** [session.config.ts](../session.config.ts) holds the provider
  (`auto`/`local`/`jev`), Jev model and minimum confidence, extra
  instructions, timing margins, slot count, phrase length, OSC port, and extra
  or replacement patterns per instrument.
- **Patterns:** each is `{ id, description, energy range, suits, render }` in
  [src/server/session/patterns](../src/server/session/patterns). The
  description is what the decision model chooses by.
- **New decision models:** another one is a `DecisionProvider` with a
  `decide(request, { timeoutMs })` method.
- **Environment:** `TYPESAFE_API_KEY` (read from `.env`), `TYPESAFE_BASE_URL`,
  `SESSION_PROVIDER`, `SESSION_OSC_PORT`.

## Verification

- **Unit tests** (`bun test`, 81 tests):
  - chord, key and loop detection
  - every pattern rendering valid notes on the chord
  - OSC decoding and bar cutting
  - audio note detection
  - the scheduler on a fake clock: firing on time, ring slots, kept clips, stopped transport, slow models cut off, late writes not fired, switching off
  - Jev request shape against a fake `fetch`
- **End to end against the mock bridge** (`bun run mock`):
  - The mock includes clips, launch-quantized playback, device parameters, and a scripted band on Bass, Keys and Vocals. The Vocals part arrives as pitch readings.
  - At 80, 120 and 160 BPM: no missed bars, clips in place about 150 ms or more before their bar, and the guitar's chords matched the band from bar 6 on.
- **Real Jev on the mock band:**
  - All decisions came from Jev, in 60–190 ms, with no missed bars.
  - Testing found two problems, both fixed: early-played straight eighths were described as syncopated (grid rounding), and Jev asked for fills in bars that start a phrase (fills are now gated to phrase ends).
- **Not yet verified in Ableton Live itself.**

## Known limits

- Every clip write adds steps to Live's undo history (fewer when clips are kept).
- Session View only. The player needs its own track: launching a scene also launches the player's slot in that row.
- Until a progression has been heard once, the next chord is a guess (the last chord held), so bars 2–5 can clash.
- Audio input hears one note at a time and may make octave errors.
- A Drum Rack inside an Instrument Rack can't report which note plays which sound in Live 11; the standard layout is assumed.
- A synth's sound is judged from names and its amp envelope only; a preset with an uninformative name and an unusual envelope may be described vaguely.
- The bridge (LiveAPI.amxd) logs every call to Max's console, and asking for `value_items` on non-enum parameters logs errors there; both are harmless.

## Later

- **Next chord from clips:** read the notes of the band's playing clips to know the next bar's chord for sure. In progress.
- **Chords from audio:** detect chords from polyphonic audio (chroma, or basic-pitch about a bar behind).
- **Your clips as options:** let your own clips in the player's track become candidates the model can choose.
- **Generated options:** candidates from generative models (magenta.js, MIDI-GPT).
- **Arranger:** a slower LLM "arranger" every 4–8 bars that sets style and density for the per-bar decisions.
- **Device face:** a web view inside the Session Player device showing its decisions.
